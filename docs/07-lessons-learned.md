# 7. 발견하고 고친 문제들

개발·평가 과정에서 실제로 틀렸다가 원인을 찾아 고친 것들만 모았다. "이렇게 설계했다"가 아니라
"이렇게 하려다 틀렸고, 이래서 틀렸다는 걸 알았고, 이렇게 고쳤다"만 다룬다.

## 리랭킹: pointwise → listwise

**문제.** CrossEncoder(`bge-reranker-v2-m3-ko`)로 후보를 하나씩 독립 채점했더니, 어휘만 겹치는
오답에 정답보다 훨씬 높은 점수를 주는 일이 반복됐다.

**구체적 사례.** `"M402ND 냉장고 온도 설정 방법 알려줘"` 질문에서, 트러블슈팅 문단("설정 온도를
확인했나요? 낮게 설정하세요" — "설정"·"온도" 단어만 겹침)에 **0.976점**을 주고, 진짜 정답("상칸
버튼을 눌러 온도를 조절" — 방법은 정확히 설명하지만 "설정"이란 단어를 안 씀)에는 **0.098점**을
줬다. 후보 수를 3~6개로 줄여도(`SQ07GA3WBN` "문이 안 열려요" 사례에서 청소 안전수칙 문단이 진짜
정답 "LG ThinQ로 고장 진단하기"보다 높은 점수를 받음) 똑같이 발생해 후보 수 문제가 아니라 판단
방식(pointwise, 어휘 유사도 의존) 자체의 한계로 결론 냈다.

**고침.** 후보를 하나씩 채점하지 않고 한 번에 놓고 비교시키는 listwise LLM(gpt-4o-mini) 판정으로
교체했다. 어휘가 아니라 내용을 읽고 상대 비교하게 해서 이 함정을 피한다.

## 리랭킹: 질문에 남은 모델 코드가 점수를 붕괴시킴

**문제.** `where={"product_model": ...}` 필터로 이미 검색 범위를 모델 하나로 좁혀놨는데, 질문
텍스트에 그 모델 코드("M402ND" 등)가 그대로 남아 있으면 리랭커가 이걸 노이즈로 읽어 정답 청크
점수를 raw logit -13대(0.000014)까지 뭉갰다. 모델명만 뺀 동일 질문으로는 0.9964 — **7만 배 차이**.
벡터 검색 순위도 소폭 개선됐다(예: `GC-B40BSCQ` "제어창" 청크 22등→12등).

**고침.** 서브 질문마다 알고 있는 모델 코드를 정규식으로 제거(`_strip_known_models`)한 뒤 검색·
리랭킹에 넣는다. 모델 스코프는 이미 `where` 필터가 맡고 있으니 텍스트에 또 들어갈 필요가 없다.

## 정답 라벨링: 순환성 있는 라벨셋

**문제.** 정답 판정을 "벡터 검색 top-20 안에서 LLM이 고르게" 했다. 이러면 판정 자체가 검증하려는
검색 엔진에 종속돼(그 엔진이 후보에서 뺀 진짜 정답은 "없다"로 판정될 수밖에 없음) 순환적이고,
top-20 밖에 정답이 있는 질문은 전부 "no_answer_in_doc"으로 버려져(150문항 중 53개) 생존 편향까지
겹쳤다 — 어려운 질문이 애초에 벤치마크에서 빠지는 구조였다.

**고침.** 검색 단계를 아예 거치지 않고 모델별 청크 전체(모델당 26~128개)를 통째로 보여주고
판정시키는 방식으로 바꿨다. 검색 결과와 독립적인 정답 판정이라 순환성이 없다.

## 정답 라벨링: 목차와 포괄 챕터가 정답으로 잘못 뽑힘

**문제.** 위 방식으로 재라벨링해도 리랭킹 "미스"의 상당수가 실제로는 라벨 자체의 오류였다. 목차
페이지("제품 사용설명서")가 우연히 질문 키워드를 포함한다는 이유만으로 서로 다른 5개 질문의
정답으로 잘못 뽑히거나, "설치 관련" 같은 포괄적 안전수칙 챕터가 "안심하세요! 고장이 아닙니다" 같은
전용 FAQ 챕터보다 정답으로 우선됐다. 28건의 미스를 원문 대조한 결과 21건이 이 패턴이었다.

**고침.** 심사 프롬프트에 "목차·색인 제외", "키워드만 스치고 실제 설명 없는 후보 제외", "포괄보다
전용 챕터 우선"을 명시했다. 완전히는 못 잡았지만(재확인 결과 잔여 미스의 상당수가 여전히 같은
패턴) 히트율이 65.7%→71.2%로 실측 개선됐다.

## 리랭킹: 손실을 줄이려던 시도는 모두 실패 (위치 편향 가설은 정정)

**문제.** 리랭킹 전 거리순위와 최종 히트 여부를 겹쳐보니 1~5등은 91.9%가 살아남는데 11~20등은
25.0%로 급락했다 — 리랭커가 내용뿐 아니라 프롬프트에서 몇 번째로 나왔는지에도 끌려간다는 뜻이라고
해석했다.

**정정(2026-09-26).** 그 표는 순위(모델 코드를 제거한 질문 기준)와 히트(원문 질문 기준)를 서로 다른 검색
결과에서 가져와 짝지은 계산이었다. 리랭커가 실제로 본 풀 기준으로 다시 계산하니 11~20등의 생존율은 25%가
아니라 54%였고, "특정 구간에서 급락"하는 모양은 재현되지 않았다. 아래 시도들의 결과(셔플·CoT 하락)는 같은
라벨셋에서의 상대 비교라 그대로 유효하지만, 시도의 동기였던 위치 편향 가설은 근거가 약해졌다.

**시도 1: 순서 셔플.** 후보를 무작위로 섞어서 다시 돌렸더니 11~20등 구간은 소폭 올랐지만
**전체 히트율이 71.2%→61.5%로 오히려 떨어졌다.** 거리순 정렬이 잡음이 아니라 "가까운 것 = 더
관련 있을 확률도 높다"는 실제 신호와 겹쳐 있어서, 순서를 없애면 원래 잘 맞히던 상위권까지 같이
나빠졌다.

**시도 2: CoT(개별 판단 강제).** 순서는 그대로 두고 후보마다 관련성 판단을 한 줄씩 먼저 쓰게 한 뒤
순위를 내게 했더니 **49.5%까지 더 떨어졌다.** 후보가 많을 때(최대 35개) 개별 판단을 전부 쓰게 하면
형식이 깨지거나 판단 자체가 흐트러지는 것으로 보인다.

**확인만 하고 도입 안 함: 앙상블.** 정렬 결과와 셔플 결과를 합치면(둘 중 하나라도 맞히면 인정)
71.2%→75.0%로 오른다 — 실제로 존재하는 개선 여지지만, 병합 로직 구현과 비용 2배가 필요해
도입하지 않았다.

**시도 3: 더 강한 리랭킹 모델(gpt-4o, 2026-09-26).** 같은 후보 목록·프롬프트로 gpt-4o-mini와 gpt-4o를
비교했더니 73 대 74/104로 사실상 같았다(둘 다 실패 24건). 모델 성능이 손실의 원인이 아니라는 뜻이다.

**결론.** 시도한 세 수정(순서 섞기, CoT, 더 강한 모델) 모두 개선하지 못했다. 그리고 손실로 보이던 것의
상당수는 리랭커가 아니라 **정답 라벨**의 문제였다(아래 소절). 리랭킹 손실을 줄이는 방법은 지금 미해결이 아니라
"측정 자체를 고쳐야 한다"로 결론을 바꿨다.

## 평가: 정답 라벨의 오류를 실패 건 감사로 발견

**문제.** 리랭킹 실패로 세던 24건(두 모델이 모두 놓친 건)을 라벨 청크와 리랭커가 고른 5개를 나란히 놓고
직접 읽었더니, 라벨 부적절 16건(목차 3건 포함, 안전수칙 같은 포괄 청크, 키워드조차 없는 무관한 청크),
라벨 협소 6건(리랭커가 고른 청크도 유효), 판단곤란 2건이었고 **리랭커가 진짜 놓친 건은 0건**이었다. 라벨
청크 하나만 정답으로 세는 지표에서 리랭커가 전용 챕터를 올바르게 골라도 미적중이 된 것이다.

**교훈 1: 실패 건만 감사하면 한쪽으로 기운다.** 성공한 건 중 무작위 20건도 라벨을 확인했더니 4건(20%)이
부실했다. 그래서 "실패의 67%, 성공의 20%가 라벨 문제"로 양쪽을 같이 보고 71.2%를 하한선으로 다룬다.

**교훈 2: 라벨을 시스템 출력으로 고치면 안 된다.** 리랭커가 고른 청크로 정답을 바꾸면 시스템 출력으로
시스템을 채점하는 순환이 된다. 이 프로젝트가 앞서 겪은 "검색 결과 안에서 정답을 고른 라벨" 문제와 같은
유형이라, 출처를 가린 재라벨링(정답 다중 허용)을 따로 했다(교훈 4).

**교훈 3: 지표들의 검색 기준을 맞춰야 한다.** Recall@K 지표는 모델 코드를 뺀 질문으로, 리랭킹 스윕은 원문
질문으로 검색해서 두 지표를 나란히 놓고 "리랭킹 손실"을 계산한 것이 어긋나 있었다. 서로 다른 조건의 숫자를
한 표에 놓지 않는다.

**교훈 4: 라벨을 고치면 결론의 크기가 바뀐다.** 104문항 전체를 출처를 가리고 다중 정답으로 다시 판정했더니(Claude 1인
판정, 692쌍) 기존 라벨은 62.5%만 질문에 직접 답하는 청크였고, top-5 적중은 리랭크 73.1%→92.3%(엄격)로,
vector-only 60.6%→84.6%로 올라갔다. 리랭킹 이득은 +13문항→+8문항으로 줄었지만 방향은 그대로였다(반대 방향 0건).
"이득이 있다"는 결론은 견고하고, 이득의 크기와 71.2% 같은 절대 수치는 정답 라벨이 좌우한다는 뜻이다. 스윕도 다시 재보니 pool
15~40은 여전히 구분되지 않았고, top_k는 3→5 이득이 +14문항에서 +2문항으로 줄었다(옛 라벨이 좁아 부풀려져 있었다). 다만
판정자가 1명이고 top_k=3의 최종 답변 품질은 측정하지 않았다.

## 웹 서비스: 실험 하니스에만 있던 로직이 실제 서비스에 안 붙어 있었음

**문제.** round1(300문항) 평가에서 실패 23건 중 13건이 "에러 메시지 확인하는 방법" 유형이었다.
질문에 에러코드가 없으면 RDB 정확매칭 경로를 타지 못하고, 벡터 검색은 질문에 "에러"라는 단어가
원문에 없으면 관련 챕터를 놓쳤다. 원인은 모델별 트러블슈팅 챕터를 구조적으로 찾아 우선 후보로
꽂아주는 로직이 실험 하니스에만 연결돼 있고 웹 서비스(`web/rag_service.py`)엔 아예 빠져 있었던 것.

**고침.** 그 로직을 웹 서비스에 연결했다. 연결한 뒤에도 일부는 검색이 맞는 챕터를 찾고도 생성
단계에서 제목만 보고 오판해 거절해서, 그 근거가 사전 검증된 정답이라는 걸 명시적으로 표시하도록
코드를 고쳤다(`build_web_context`). 13건 중 12건 정상화, 나머지 1건은 애초에 그 모델 설명서에
화면 에러 코드 표시 자체가 없어 "설명서에 없다"가 정답인 케이스였다.

## 데이터: FAQ 합성질문 컬렉션 — 도입했다가 효과 없어서 제거

**문제/시도.** 검색 재현율을 높이려고 매뉴얼 청크마다 예상 질문(FAQ)을 미리 생성해 별도 컬렉션에
넣고, 질문이 들어오면 이 FAQ 컬렉션도 함께 검색해 매칭된 FAQ의 원본 청크를 병합하는 방식을
시도했다.

**결과.** 60개 모델 중 12개에만 생성돼 있었고, 97문항으로 재검증한 결과 실측 효과가 0이었다.

**고침.** 컬렉션 자체를 제거했다. 효과가 측정되지 않는 복잡도는 유지 비용만 남긴다고 판단했다.

## 공유 DB 전환: Chroma와 Postgres의 숨은 차이 두 가지

**문제.** 로컬(SQLite+Chroma)에서 공유 DB(Postgres+pgvector)로 옮기면서 "검색 결과가 달라지지
않아야 한다"는 걸 검증하다가 두 가지를 발견했다.

1. Chroma의 `get(ids=[...])`는 요청한 순서가 아니라 **컬렉션 내부 순번**으로 결과를 돌려준다 —
   그대로 옮기면 리랭킹 후보 순서가 바뀌는 버그가 됐을 것.
2. Postgres의 한글 정렬이 SQLite와 다르다.

**고침.** 무작위 질의 80건으로 벡터 검색 상위 40개 순서 100% 일치, `get(ids)` 200회 전부 일치,
매뉴얼/에러코드/기능 유무 조회까지 전수 대조한 뒤 전환했다.

## 정답 라벨링: 이중 재시도로 문항당 11분씩 물고 늘어짐

**문제.** 재라벨링 스크립트가 `RateLimitError`로 중간에 죽는 걸 고치려고 재시도 로직(3회, 20/40/80초
백오프)을 추가했는데, 이미 내부적으로 재시도하는 `generate_openai()`(5회, 매 시도 최대 31초 대기 +
30초 타임아웃) 위에 또 감싼 셈이 돼서 최악의 경우 한 문항이 11분 넘게 멈춰 있는 이중 재시도가 됐다.
두 번 연속 같은 지점에서 재현되고 나서야 원인을 찾았다.

**고침.** 바깥쪽 재시도를 없앴다. 한 번 실패하면 바로 에러로 넘기고, 10개마다 중간 저장한 체크
포인트에서 `--resume`으로 이어받는 쪽이 훨씬 단순하고 안전했다.
