# 카테고리 공통 Fallback DB 구축 전략

> **⚠ 보류 (2026-09-11) — 진행 안 하기로 결정.**
> 미등록 모델에 대한 "카테고리 범용 조치법" 답변은 특정 문서에 근거한 게 아니라 사실상 LLM의
> 사전지식으로 답하는 것과 다르지 않다. 즉 GPT/Claude 등 최신 모델에 그냥 물어봐도 비슷한
> 품질의 답을 이미 잘 준다 — RAG(문서 근거·인용)의 차별점이 없는 영역이다. 여기에 임베딩
> 클러스터링·태깅 파이프라인을 투자하는 건 과잉 엔지니어링이라고 판단해 중단.
>
> **대신 확정한 범위**: 상품 등록(모델 DB 존재)이 전제라고 가정한다. 미등록 모델 질문에
> 대한 대응, 그리고 새 모델을 계속 DB에 편입시키는 자동 크롤링/확장은 실제 서비스화 시점의
> "LLMOps 영역" 향후 과제로 넘긴다. 지금 우리 목표는 등록된 모델에 대해 RAG 검색·답변
> 품질을 얼마나 정확하게 만드느냐이지, 콜드스타트 커버리지가 아니다.
>
> 아래 원래 문서는 그 논의 과정과 근거를 남겨두기 위해 그대로 보존한다.

## 배경

현재 검색 흐름(`pipeline/query_engine.py`)은 2단계뿐이다.

1. 질문에 등록된 모델명이 정확히 언급되면 `product_model` 필터로 검색
2. 아니면 필터 없이 전체 청크에서 검색

즉 "등록 안 된 모델"과 "아무 힌트도 없는 질문"이 똑같이 취급된다. 하지만 실제로 LG 에어컨 두 모델(FQ18GU1BHN, FQ16FV6EDN)의 "냄새 제거하기" 섹션을 비교했을 때 텍스트 유사도가 **98.78%**로 나온 것처럼, 냉방 불량·누수·소음 같은 핵심 증상의 조치법은 브랜드·모델과 거의 무관하게 동일하다. 이 사실을 그대로 활용해서 중간 단계를 하나 추가한다.

## 목표 검색 흐름 (3단계)

1. **정밀 검색** — `product_model` 정확 매칭 (기존 그대로)
2. **카테고리 폴백 (신규)** — 모델 매칭 실패 또는 1단계 결과의 유사도가 임계치 미만일 때, `category` + `symptom_class` 로 필터를 완화해서 브랜드 무관 검색
3. **전체 폴백** — 그래도 없으면 필터 없이 전체 검색 (기존 그대로, 최후 수단)

핵심은 2단계다. "브랜드=범용" 같은 별도 문서를 새로 만드는 게 아니라, **기존 청크 중 카테고리+증상이 같은 걸 브랜드 무관하게 그냥 가져오는 것**이다. 어차피 그 내용 자체가 브랜드 무관하게 거의 동일하다는 게 이미 검증됐기 때문에, 별도의 "Global 문서"를 관리할 필요가 없다.

## 메타데이터 스키마 확장

기존 청크 메타데이터(`product_model`, `category`)에 `symptom_class` 한 필드만 추가한다.

```
{"product_model": "FQ18GU1BHN", "category": "에어컨", "symptom_class": "냉방불량"}
```

### symptom_class 후보 taxonomy (초안, 카테고리 공통)

| symptom_class | 예시 |
|---|---|
| 전원/작동안됨 | 전원이 안 켜져요, 갑자기 꺼져요 |
| 냉방·냉각 불량 | 시원하지 않아요, 냉기가 약해요 |
| 소음 | 이상한 소리가 나요 |
| 누수/배수 | 물이 새요, 물이 넘쳐요 |
| 냄새 | 냄새가 나요 |
| 에러/표시부 | 화면에 코드가 떠요 (※ 이미 RDB가 담당하는 영역과 겹치므로, 에러코드가 명시된 질문은 기존 `find_codes_in_text` 경로가 우선) |
| 설치/이동 | 설치 후 문제, 이전설치 |
| 사용법/기능 | 특정 기능 사용 방법 |

이 목록은 실제 청크 분포를 보고 카테고리별로 조정이 필요하다. 지금은 초안일 뿐이다.

## Global(카테고리 공통) 데이터를 "효율적으로" 만드는 법

가장 중요한 원칙: **사람이 "이 섹션은 공통이다"를 수동으로 읽고 판단하지 않는다.** 이미 발견한 98.78% 유사도 자체가 자동 탐지 신호가 된다.

1. 카테고리별로 전체 청크를 임베딩 유사도로 클러스터링한다.
2. 서로 다른 `product_model`인데 코사인 유사도가 임계치(예: 0.9~0.95) 이상인 클러스터가 나오면, 그 클러스터는 정의상 "모델 무관 범용 내용"이다.
3. 이런 클러스터에 한해서만 `symptom_class`를 태깅하면 되므로, 전체 청크를 다 들여다볼 필요가 없다 — 클러스터링이 먼저 후보를 걸러준다.

### symptom_class 태깅은 1회성 배치 작업

- 매 사용자 질문마다 태깅하는 게 아니라, **기존에 이미 임베딩된 청크(현재 LG 2,185개 + 삼성 추가분)에 대해 한 번만** 저가 LLM(`gpt-4o-mini` 등)으로 라벨을 매겨서 메타데이터에 채워 넣는다.
- 일회성 구축 비용이라 저렴하고, 이후 새 모델이 추가될 때만 그 모델 청크에 대해서만 증분으로 태깅하면 된다.

### 중복 제거(dedup)

같은 내용이 카테고리 안에서 10개 모델에 반복되므로, 2단계(카테고리 폴백)에서 top-k를 그냥 뽑으면 사실상 똑같은 문장이 3번 나올 위험이 있다. 클러스터당 대표 청크 1개만 골라 검색 결과 후보에 넣는 방식으로 정리한다 (대표 선정 기준은 클러스터 중심에 가장 가까운 청크, 혹은 최초 수집 브랜드 우선 등 — 추후 결정).

## 사용자 질문에서 symptom_class 추출하는 법

**별도로 학습된 분류기는 만들지 않는다.** 라벨링된 학습 데이터가 없고, taxonomy가 작고 고정돼 있어서 굳이 모델을 하나 더 유지보수할 이유가 없다. 대신 기존 `find_model_in_text()`와 같은 철학으로 2단 처리한다.

1. 키워드 사전 매칭 (예: "시원하지 않", "냉방", "물이 새", "소음" 등) — 비용 0, 즉시 처리
2. 키워드가 안 걸리면 그때만 가벼운 LLM 호출로 `{category, symptom_class}` 구조화 추출

이건 질문 시점마다 도는 로직이라 DB 구축 자체와는 별개지만, 2단계 폴백 검색이 실제로 동작하려면 반드시 필요한 짝이다.

## 실행 체크리스트 (제안 순서)

1. symptom_class taxonomy 확정 (카테고리별 실제 청크 분포 확인 후 조정)
2. 기존 청크 임베딩 유사도 클러스터링 → 카테고리 공통 클러스터 식별
3. 식별된 클러스터에 한해 1회성 배치 LLM 태깅 → 메타데이터에 `symptom_class` 채움
4. `_answer_from_vector()`에 2단계(카테고리+증상 폴백) 추가, 임계치 기반 분기
5. 질문 쪽 symptom_class 추출기(키워드 우선 + LLM 폴백) 작성
6. 2단계 전용 시스템 프롬프트 추가 (기존 `EXACT_MODEL_SYSTEM_PROMPT` / `GENERAL_SYSTEM_PROMPT`에 이어 세 번째)

## 아직 정해야 할 것

- symptom_class 최종 개수·이름
- 1→2단계로 넘어가는 유사도 임계치 값 (실험으로 튜닝 필요)
- 클러스터 대표 청크 선정 기준
- symptom_class 태깅을 Postgres/pgvector 스키마의 `metadata JSONB`에 넣을지, 별도 컬럼으로 뺄지 (검색 인덱스 성능 고려)
