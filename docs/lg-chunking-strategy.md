> **✅ 업데이트 (같은 날)**: 아래 "실행 우선순위 제안" 1~4번 전부 `pipeline/pdf_chunker.py`에
> 구현하고 LG 30개 문서 전체로 재검증 완료. 그림/OCR 추출(`pipeline/figure_extractor.py`)도
> 신규 구현. 상세 내용은 문서 맨 아래 "구현 완료 내역" 참고. 벡터DB 재적재(임베딩)는 아직
> 안 함 - OpenAI API 키 필요, 별도 승인 후 진행.

`pipeline/pdf_chunker.py`를 LG 30개 PDF 전체에 실제로 돌려서 나온 진단 수치를 바탕으로 정리했다. 삼성은 아직 미적재라 이번 점검에서는 제외 (LG만).

## 결론 먼저

지금 로직(TOC 우선 → 없으면 폰트 폴백, `MAX_CHUNK_CHARS=700`으로 뒤에서 균등 슬라이싱)은 **30개 중 26개에서는 잘 작동**하지만, 4가지 패턴에서 문제가 확인됐다. 전부 "문서가 다르게 생겨서" 생기는 문제이지 코드 버그는 아니다 — LG가 매뉴얼마다 실제로 다른 방식으로 조판했기 때문.

| # | 문제 유형 | 영향 문서 수 | 심각도 |
|---|---|---|---|
| 1 | TOC가 아예 없어서 폰트 폴백이 쓰레기 청크를 만듦 | 2개 | 높음 |

## 문제 1: TOC 없음 → 폰트 폴백 품질 저하

**대상**: `RF_S825AW35.pdf`, `RF_S835S31.pdf` (냉장고 2개, 둘 다 같은 계열 변형이라 증상 동일)

이 두 파일만 `doc.get_toc()`가 빈 리스트를 반환해서 `extract_sections_by_font()`로 폴백한다. 실제 추출 결과(`RF_S825AW35.pdf`):

```
p  2  len=13463  heading='리니어압축기적용으로초절전, 초저소음실현'   ← 페이지 2~30 전체가 통짜 1섹션
p 31  len=   80  heading='3 표시창이꺼진상태에서첫번째버튼터치시...'  ← 주의사항 목록의 "3번" 항목이
p 31  len=   30  heading='5 버튼선택문구위에이물질이있거나...'         잘못 헤딩으로 인식됨
p 31  len=   21  heading='6 표시창버튼은터치감지방식으로...'
p 48  len=  289  heading='䤏'                                        ← 깨진 특수문자가 헤딩으로 인식
```

두 가지 반대 방향의 문제가 동시에 발생:
- **과소 분할**: 실제 사용법 본문(냉방/냉장 핵심 기능 설명)이 통째로 13,463자 한 섹션 → 뒤에서 700자씩 기계적으로 잘려 19조각이 되는데, 각 조각에 원래 헤딩("리니어압축기적용으로...") 하나만 붙어서 실제로 어떤 기능 설명인지 문맥이 사라짐.
- **과다 분할**: "주의사항" 안내문의 번호 매긴 목록 항목(3, 5, 6...)이 폰트 크기 때문에 헤딩으로 오인식되어 의미 없는 초소형 섹션을 양산.

**원인**: 이 두 매뉴얼은 본문 폰트 크기 체계가 다른 LG 매뉴얼과 달라서(부제목이 `HEADING_SIZE_THRESHOLD=12.4`를 못 넘거나, 반대로 목록 번호가 넘음) 휴리스틱이 안 맞는다.

**대응 방향**:
- 이 2개 파일은 폰트 임계값을 일괄 튜닝해서 해결하려 하지 말 것 (다른 28개에 영향 줄 위험). **파일 단위 예외 처리**가 맞다.
- 가장 현실적인 방법: 이 2개만 수동으로 페이지 구간을 지정해 섹션을 나누거나(하드코딩 맵), 최소한 "과소 분할된 큰 섹션(13,463자)만이라도 문단 단위(빈 줄 기준)로 재분할"하는 별도 함수를 하나 추가해서 이 케이스에만 적용.
- 우선순위는 낮음 — 냉장고 30개 모델 중 2개뿐이고, 실사용 시 완전히 검색 불가능한 건 아니라 "품질 저하"이지 "결측"은 아님.

## 문제 2: TOC는 있지만 특정 챕터가 과도하게 큼 (제일 중요)

**대상 확인됨**: `WM_FC2521KX6C.pdf` (세탁기, 92페이지)

```
p 32  len=19946  heading='세탁 코스 및 옵션 사용하기'   ← 페이지 32~57, 25페이지 통짜
p 76  len=11828  heading='문제 해결하기'                ← 페이지 76~85, 10페이지 통짜
```

`extract_sections_from_toc()`가 `max_depth=2`까지만 경계로 쓰는데, 이 문서는 "세탁 코스 및 옵션 사용하기" 아래 실제로는 코스별(면/울/속옷/급속 등) 레벨3 하위 목차가 있을 텐데 지금 로직이 거기서 안 끊는다. 19,946자를 700자로 자르면 **28조각**이 나오고, 어느 조각이 "울 코스" 얘기인지 "합성섬유 코스" 얘기인지 헤딩만 봐서는 구분이 안 된다.

**이게 왜 제일 심각한가**: "문제 해결하기" 챕터가 똑같은 문제를 겪는다 (11,828자, 17조각). 이 프로젝트의 존재 이유가 "고장 증상 → 정확한 조치법"인데, 정작 트러블슈팅 챕터가 가장 거칠게 잘리는 셈이다. 사용자가 "탈수가 안 돼요"라고 물었을 때, 관련 내용이 17조각 중 어딘가에 파묻혀 있고 청크 헤딩은 전부 "문제 해결하기"로 동일해서 벡터 검색 품질이 떨어진다.

**다른 문서들도 위험군**: 위 표에서 `max_len`이 6,000자를 넘는 문서가 다수 있다(FQ16FV6EDN 9,032 / FQ17FN5BDN·FQ18GN7BKN·FQ25GN9BKN 9,863 / WM_FH23KN 11,889 등). 전부 확인하지는 않았지만 같은 패턴(레벨3 미반영)일 가능성이 높다.

**대응 방향**:
- `extract_sections_from_toc()`에 **"섹션이 일정 길이(예: 3,000자)를 넘으면 그 섹션 구간에 한해 `max_depth`를 3~4로 올려서 재귀적으로 다시 쪼갠다"** 는 조건부 로직 추가를 추천. 지금처럼 문서 전체에 고정 `max_depth=2`를 적용하는 대신, 큰 섹션만 선택적으로 더 깊이 들어가는 방식.
- 특히 **"문제 해결하기"/"고장 진단하기" 헤딩은 항상 강제로 max_depth를 최대치로 풀어서** 레벨3(에러코드별/증상별 하위 항목)까지 전부 개별 청크가 되게 하는 카테고리 특례를 두는 게 비용 대비 효과가 가장 크다. 이 프로젝트 목적에 가장 직결되는 챕터이기 때문.

## 문제 3: 챕터 제목 중복 (복합기기 매뉴얼)

두 가지 서로 다른 이유로 발생한다.

**(A) 아이컨 10개 전부 공통** — "추가 기능 및 설정하기"가 리모컨 조작용(6,627자)과 유선 조작부용(749자) 두 번 등장. 하나의 기기에 두 가지 조작 방식이 있어서 매뉴얼이 챕터를 두 번 쓴 것.

**(B) 워시타워/콤보 매뉴얼** — `DR_RH21E5ATKWP.pdf`(6개 중복), `WM_FA25AJPB.pdf`(5개 중복)는 세탁기+건조기가 한 매뉴얼에 같이 있어서 "제품 청소하기", "제품 관리하기", "겨울철 동결 해결하기" 등 챕터 세트 전체가 세탁기 파트/건조기 파트에서 통째로 반복된다.

지금 메타데이터는 `section_title`에 원본 헤딩을 그대로 저장하므로, 두 케이스 다 **서로 다른 내용의 청크 2개가 완전히 동일한 `section_title` 값**을 가지게 된다. 검색 자체는 벡터 유사도로 되니까 당장 안 깨지지만, `section_title`로 필터링/그룹핑하는 기능을 나중에 추가하면 이 두 챕터가 섞여 보인다.

**대응 방향**:
- (B)가 더 중요 — 세탁기와 건조기는 `category`가 사실상 다른데 지금은 파일 하나 전체에 `category="세탁기"`를 일괄 적용하고 있을 것이다(수집 스크립트 기준 확인 필요). 최소한 **중복된 헤딩이 나오는 지점부터는 상위 컨텍스트(예: "건조기 파트"라는 접두어)를 heading에 붙이는 로직**을 추가해서 `[건조기] 제품 청소하기` / `[세탁기] 제품 청소하기` 로 구분되게 하는 걸 추천.
- (A)는 우선순위 낮음 — 리모컨용/조작부용 구분이 실제 사용자 질문에 크게 영향 안 줌.

## 문제 4: 문서 간 청크 개수 편차 (33~140개) — 정상, 조치 불필요

`WM_FA25AJPB.pdf`(140청크, 100페이지)와 `RF_CA-H17DC.pdf`(33청크, 43페이지)처럼 최대 4배 차이가 난다. 이건 **매뉴얼 자체의 실제 분량 차이**이지 청킹 로직 문제가 아니다. 인위적으로 청크 수를 맞추려고 하지 말 것 — 짧은 매뉴얼을 억지로 더 잘게 쪼개거나 긴 매뉴얼을 압축하면 오히려 내용 왜곡이 생긴다. 다만 "이 모델은 문서가 짧아서 애초에 검색 후보가 적다"는 사실은 결과 해석 시 참고할 만하다.

## 실행 우선순위 제안

1. **(최우선)** "문제 해결하기"/"고장 진단하기" 챕터는 max_depth 제한 없이 최하위 레벨까지 강제로 세분화 — RAG 목적과 직결.
2. **(우선)** 섹션 길이 임계치(예: 3,000자) 초과 시 해당 구간만 재귀적으로 더 깊은 TOC 레벨 적용.
3. **(선택)** 워시타워형 복합 매뉴얼은 중복 챕터명에 파트 구분 접두어 추가.
4. **(낮음, 나중에)** `S825AW35`/`S835S31` 폰트 폴백 결과를 페이지 구간 수동 지정으로 교정.
5. 청크 개수 편차(문제4)는 손대지 않는다.

삼성 30개는 아직 미적재라 이 점검에 포함하지 않았다 — 적재 시점에 동일한 방식으로 재점검 필요.

## 구현 완료 내역 (2026-09-11)

### 1~3번 (트러블슈팅 강제 세분화 / 긴 섹션 재귀 분할 / 중복 제목 disambiguation)

`extract_sections_from_toc()`를 트리 기반으로 재작성했다.

- TOC를 평면 리스트가 아니라 중첩 트리로 변환(`_build_toc_tree`)한 뒤, "문제 해결"/"고장 진단"
  등 트러블슈팅 키워드가 제목에 있으면(`TROUBLESHOOTING_KEYWORDS`) 자식이 있는 한 리프
  레벨까지 무조건 내려간다(`_select_nodes`).
- 그 외 섹션은 기존처럼 `max_depth=2`로 자르되, 텍스트가 3,000자(`MAX_SECTION_CHARS_BEFORE_SPLIT`)를
  넘으면 한 단계 더 깊은 TOC 레벨로 재귀적으로 대체한다(`_expand_if_too_long`). 더 쪼갤 하위
  레벨이 없으면(TOC에 그 이상 정보가 없으면) 있는 그대로 둔다 - 예: `WM_FC2521KX6C.pdf`의
  "사용 관련"(8,159자)은 TOC 최심 레벨이라 더 못 쪼갬, 이건 LG 매뉴얼 자체의 한계.
- 같은 제목이 중복되면(워시타워형 세탁기+건조기 통합 매뉴얼) 조상 경로를 필요한 만큼만
  붙여서 구분한다(`_disambiguate_titles`) - 직속 부모로 안 갈리면 조부모까지 자동으로
  올라간다. **재검증 결과: LG 30개 문서 전체에서 `dup_headings: 0`으로 전부 해소됨.**

재검증 수치(변경 전 → 후): `WM_FC2521KX6C.pdf` 24개 섹션(최대 19,946자) → 51개 섹션(최대
8,159자), `AC_FQ16FV6EDN.pdf` 최대 섹션 길이 9,032자 → 2,698자, `DR_RH21E5ATKWP.pdf`
중복 헤딩 6개 → 0개.

### 4번 (FONT 폴백 - TOC 없는 문서)

`RF_S825AW35.pdf`, `RF_S835S31.pdf`(TOC 없음) 대상. TOC가 없어서 "하위 레벨로 대체"가
불가능하므로, 대신 **줄(line) 경계를 유지하면서** 3,000자 단위로 재그룹핑하는
`_group_lines_by_size()`를 추가했다 - 문장/단어 중간이 아니라 최소한 원래 텍스트 줄 단위에서
잘리게 한다. 결과: 13,463자 통짜 섹션 → 24개 섹션(최대 2,997자)으로 개선. 다만 번호 매긴
주의사항 목록이 헤딩으로 오인식되는 과다분할 문제는 그대로 남아있음(우선순위 낮음, 원문
그대로 두기로 함).

### 5번 (신규) — 그림/OCR 추출: `pipeline/figure_extractor.py`

실제 확인해보니 LG 매뉴얼의 다이어그램(리모컨 그림, 버튼 설명 등)은 임베디드 이미지가
아니라 **거의 전부 벡터 드로잉**으로 그려져 있다 (83페이지 문서 기준 임베디드 이미지 있는
페이지 2개, 벡터 드로잉 있는 페이지 76개). 그래서 이미지만 뽑는 방식으로는 실제 그림을
거의 못 잡는다.

대신 페이지별 "드로잉 잉크 비율"(벡터 도형 bbox 면적 합 / 페이지 면적)을 계산해서 임계값
0.15 이상이면 페이지 전체를 이미지로 렌더링한다. 실측 근거: 리모컨 그림 페이지 0.31~1.11,
법률/경고 텍스트 위주 페이지 0.00~0.09로 뚜렷하게 갈림.

- Tesseract-OCR(한국어 언어팩 확인됨) + pytesseract로 저장된 이미지에서 텍스트까지 뽑는다.
  Tesseract가 없는 환경에서도 이미지 추출 자체는 계속 동작(OCR은 best-effort).
- **중요**: OCR 텍스트는 metadata에만 넣지 않고 실제로 임베딩되는 청크 `text`에도
  `[그림 설명(OCR)] ...` 형태로 포함시킨다 - 벡터DB는 텍스트를 숫자로 바꿔 저장하는 구조라,
  그림 속 글자가 검색되려면 그 텍스트가 임베딩 대상 문자열 안에 있어야 한다 (metadata는
  필터링/표시 전용, 임베딩되지 않음).
- `metadata["figures"]`에 이미지 파일 경로 목록을 저장해서, 답변 생성 시 "이 그림을
  참고하세요"처럼 텍스트 답변과 함께 보여줄 수 있게 했다.
- 결과물은 `data/manual_figures/lg/{aircon,fridge,washer}/{model}/`에 저장 (PDF·제품사진과
  동일하게 `.gitignore` 처리, 공개 저장소에 안 올라감).
- 재실행 캐싱: 문서당 페이지 렌더링+OCR이 수십 초(테스트 기준 42페이지에 37.7초) 걸려서,
  청킹 로직을 바꿔 재적재할 때마다 매번 다시 돌리면 낭비다. `out_dir`에 `_manifest.json`이
  있으면 재계산 없이 그대로 읽어서 반환한다(`use_cache=True`가 기본값).
- `scripts_batch_ingest_all_lg.py`가 `build_documents_from_pdf(extract_figures=True, ...)`를
  쓰도록 이미 반영해뒀다 - 실제 임베딩 재적재(OpenAI API 키 필요)만 승인되면 바로 실행 가능.

### 6번 (2026-09-11 추가) — Streamlit 데모 실사용 중 발견한 3가지 실측 버그 수정

실제 Streamlit 데모(`app_streamlit.py`)로 여러 제품을 테스트하다가, 벡터DB에 실제로 들어간
청크를 직접 까보며 3가지 문제를 찾아 전부 고쳤다.

**(a) 그림-페이지 느슨한 매칭 → 청크 폭발**: TOC가 없는 문서(`RF_S825AW35.pdf` 등)는 섹션
간 페이지 간격이 최대 10페이지까지 벌어지는데, "다음 섹션 시작 전까지의 모든 그림"을 그대로
캡션으로 병합하다 보니 그림 12개(무관한 페이지 내용 포함)가 청크 하나에 붙어 4,221자까지
불어난 사고가 실측으로 확인됐다. 고침: 임베딩되는 캡션은 **그림의 실제 페이지가 섹션 시작
페이지와 정확히 일치할 때만** 병합(`MAX_CAPTIONS_EMBEDDED_PER_SECTION=3`), 화면 표시용
`metadata["figures"]`도 개수 상한(`MAX_FIGURES_DISPLAYED_PER_SECTION=5`)을 둠. 재검증: 같은
청크가 4,221자/그림 12개 → 1,081자/그림 5개로 정상화.

**(b) 최종 청크 슬라이싱 오버랩 0%**: `MAX_CHUNK_CHARS=700`을 그대로 step으로 써서 청크
경계에서 문장이 그냥 잘렸다. `CHUNK_OVERLAP_CHARS=105`(15%)를 둬서 step을 595로 줄임.

**(c) 문제해결 표의 증상이 TOC 리프 경계에서 잘림**: "냉장고 안에서 냄새가 나요"처럼 원인이
여러 개인 증상이, TOC 리프 구분(예: "부품"/"소음" 카테고리 탭) 경계에 걸려 원인 일부는
"부품" 청크에 나머지는 "소음" 청크에 흩어지는 문제가 실측으로 확인됐다(둘 다 `section_title`이
증상과 무관해서 근거 문서 표시도 헷갈림). 고침: `_resplit_troubleshooting_by_symptom()` -
같은 트러블슈팅 서브트리 산하 연속 리프 섹션들을 원문 그대로 이어붙인 뒤, "증상 문장"
패턴(불릿 아님 + 물음표 아님 + 평서문 종결 + 다음 줄이 질문)으로 재분할한다. 완벽하지
않음(가끔 "고장이 아니니 안심하세요" 같은 보충설명 문장을 증상으로 오인식해 과분할하는
부작용 있음 - 내용은 안 틀리고 제목만 가끔 어색해짐, 사용자 확인 후 이 정확도로 채택).
재검증: GC-B40BSCQ의 "냄새" 증상이 "부품"+"소음" 2개 무관 청크 대신 "냉장고 안에서 냄새가
나요" 제목의 명확한 청크로 통합됨. 30개 문서 전체 재검증 결과 `dup_headings: 0` 유지.

세 가지 수정 모두 `scripts_eval_retrieval.py`(신규)로 회귀 테스트 — 이번 세션에서 실제
테스트했던 질문 4개를 그대로 재사용해서 청크 크기/거리/키워드 매칭을 확인한다.
