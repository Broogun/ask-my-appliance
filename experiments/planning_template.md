## 6. 왜 RAG를 사용하는가?

### 6.1 일반 LLM만으로 해결하기 어려운 이유

| 항목 | 작성 내용 |
|---|---|
| 사내 또는 서비스 고유 데이터가 필요한가? | |
| 최신 정보가 필요한가? | |
| 답변의 근거가 필요한가? | |
| 잘못된 답변을 줄여야 하는가? | |
| 데이터가 지속적으로 변경되는가? | |
| 사용자가 원문을 확인할 필요가 있는가? | |

### 6.2 RAG가 필요한 이유

| 항목 | 작성 내용 |
|---|---|
| RAG가 필요한 핵심 이유 | |
| 일반 LLM 대비 이점 | |
| 단순 키워드 검색 대비 이점 | |

### 6.3 프로젝트에서 RAG가 담당하는 역할
```
사용자 질문 → 관련 정보 검색 → 필요한 근거 선별 → 검색된 정보를 기반으로 답변 생성 → 근거/출처 제공
```

## 8. RAG 설계 방향

### 8.1 초기 설계

| 설계 영역 | 검토할 방법 | 초기 선택 | 선택 이유 |
|---|---|---|---|
| 문서 분할 | Fixed-size / Recursive / Semantic / 구조 기반 | | |
| 검색 | Vector Search / BM25 / Hybrid Search | | |
| Embedding | 사용할 Embedding 모델 | | |
| 검색 결과 수 | Top-K | | |
| 검색 결과 개선 | Reranking / MMR | | |
| 질문 개선 | Query Rewrite / Multi Query | | |
| 메타데이터 | 유형 / 날짜 / 카테고리 필터 | | |
| 답변 생성 | LLM + Prompt + Citation | | |

### 8.2 문제 발생 시 검토할 개선 방법

| 관찰된 문제 | 검토할 방법 | 적용 여부/결과 |
|---|---|---|
| 정확한 키워드가 중요한데 검색이 약함 | BM25 / Hybrid Search | |
| 관련 문서는 나오지만 순서가 좋지 않음 | Reranking | |
| 질문 표현에 따라 결과가 크게 달라짐 | Query Rewrite / Multi Query | |
| 긴 문서의 문맥이 잘림 | Parent Document / 구조 기반 Chunking | |
| 중복 검색 결과가 많음 | MMR / 중복 제거 | |
| 문서 유형·기간 구분이 필요함 | Metadata Filtering | |
