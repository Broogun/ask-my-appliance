## 1. 무엇이 문제였나

`AC_FQ18GC1EHN` 한 모델로 검색 테스트(bge-m3, top_k=3)를 돌렸을 때 **top-1은 대체로
맞는데 top-2/3이 엉뚱하게** 나왔다. 재현해서 뜯어보니 검색(임베딩) 문제가 아니라
**청킹 문제**였다.

| 질문 | 개선 전 top-1 | 개선 전 top-2/3 |
|---|---|---|
| 취침 모드 어떻게 켜요? | ✅ `AI 수면(취침) 설정하기` | ❌ `리모컨 건전지 끼우기`라는 라벨의 1200자 덩어리 ×2 — 실제 내용은 리모컨 버튼 설명/냉방 사용법 |
| 와이파이 연결이 안 돼요 | ✅ 와이파이 증상 행 | ⚠ 같은 증상의 다른 원인 행. **원인 6개 중 3개만** LLM에 전달 |
| 필터 얼마나 자주 청소? | ⚠ `관리하기` 1200자 덩어리 — "12개월마다 필터 교체 / 38 / 관리하기 / 2 / 제품 뒷면에…" 표 한복판에서 시작 | 정답("극세 필터 2주에 한 번")은 top-2 청크 **맨 끝**에 있고, 그 청크 앞 900자는 UVnano 설명 |
| 이상한 냄새가 나요 | ⚠ 앞부분은 "필터 교체 알림 초기화", 냄새 제거는 중간부터 | ❌ `알아보기`(부품 명칭), `소음` 증상 행 |

### 원인 1 — `관리하기` 등 대부분 섹션이 소제목 없이 1200자 고정 분할

`parse_generic()`이 섹션 전체를 이어붙인 뒤 1200자마다 잘랐다. 그래서

- 필터 청소 주기 표가 청크 경계에서 두 동강 (`… • 2주에 한 번 권장 | 12개월마다 필터 교체 …`)
- "냄새 제거하기"가 "필터 교체 알림 초기화" 뒤에 붙어 한 청크
- `subsection`이 전부 빈 문자열이라 breadcrumb도 `관리하기 > ` 로 끝남

### 원인 2 — 사용법 챕터의 "숨은 헤더" 감지가 목차 소제목을 놓침

`parse_howto_hidden_headers()`는 "20자 이하 짧은 줄 + 4줄 안에 `1` 단독 줄"을 소제목으로
봤다. 4단계 헤더(아이스 쿨파워 냉방, 스마트 절전 냉방…)는 잡았지만, **목차에 있는 3단계
헤더**(`리모컨 처음 사용하기`, `냉방 기능 사용하기`)는 설명 문장이 4줄 넘게 이어진 뒤에 `1`이
와서 못 잡았다. 결과: 건전지 끼우기부터 냉방 사용법까지 **6,000자가 "리모컨 건전지 끼우기"
라벨로 1200자씩 5조각**. 취침 질문의 top-2/3이 이것.

### 원인 3 — 고장신고 표를 "원인 1행 = 청크 1개"로 쪼갬

959개 청크 중 **471개(49%)** 가 100~300자짜리 증상 행이었다.

- 와이파이 질문: 같은 증상의 원인 행 6개가 top-5를 독식 → LLM엔 3개만 전달돼 답이 반토막
- 냄새 질문: 무관한 `소음` 행이 top-4/5로 올라옴
- 짧은 행이 인덱스 절반을 차지해 다른 섹션이 전반적으로 불리

### 그 외 잡음

- 페이지 번호 + 러닝헤더(`⏎ 38 ⏎ 관리하기 ⏎`)가 본문 중간에 그대로 박혀 있음.
  34자짜리 `"17 ⏎ 리모컨으로 사용하기 ⏎ 리모컨으로 사용하기 ⏎ 리모컨 살펴보기"` 쓰레기 청크도 생김
- `chunk_id`를 `hash(body) % 10_000`으로 만들어 **커널 재시작마다 id가 바뀜**
  (파이썬 `str.__hash__`는 프로세스별 랜덤 시드) → 결과 JSON의 `candidates.id` 비교 불가
- `split_oversized()`가 오버랩 0으로 문장 중간을 자름
- 벽걸이형(SQ)은 챕터명이 `리모컨으로 사용하기`가 아니라 **`사용하기`** 인데
  `TOP_LEVEL_SECTIONS`에 없어서 사용법 챕터 전체가 앞 챕터 `알아보기`에 흡수됨
- `category_for_table()`이 표 위에 카테고리 제목이 없을 때(앞 페이지에서 이어진 표)
  같은 페이지 **아래쪽**의 다음 카테고리를 가져와 `운전` 표 끝부분이 `소음`으로 태깅됨

## 2. 어떻게 해결했나

### 핵심: PDF에 내장된 목차(북마크)를 청크 경계로 쓴다

LG 매뉴얼은 프레임메이커로 만들어져 `doc.get_toc()`로 3단계 목차가 그대로 나온다.
10개 PDF 전부에서 **2·3단계 제목 1,090개가 본문 줄과 글자 그대로 100% 일치**함을 확인했다
(누락 0). 1단계(대챕터)는 파일마다 중첩이 어긋나는 경우가 있어 기존 `locate_sections()`
(러닝헤더 + 제목 두 줄 연속 패턴)를 그대로 쓴다.

```
관리하기                                  ← 1단계: locate_sections()
  > 청소하기                              ← 2단계: TOC
    > 필터 청소하기                       ← 3단계: TOC        ★ 기본 청크 단위
      > (없음)
리모컨으로 사용하기
  > 냉방 기본 기능 작동하기
    > 냉방 부가 기능 설정하기
      > 아이스 쿨파워 냉방                ← 4단계: 숨은 헤더 감지 (사용법 챕터만)
```

`parse_by_toc()` 하나가 안전주의/ThinQ/알아보기/사용하기/조작부/관리하기/보증서/부록을 전부
처리한다. 페이지 `i`에서는 **목차가 그 페이지(또는 직전 페이지)에 있다고 적은 제목만** 경계
후보로 보기 때문에, 본문 안 상호참조(`~ 관리하기(필터 청소하기)를 보세요`)나 다른 페이지의
같은 단어에는 안 걸린다.

`subsection` 라벨은 `2단계 > 3단계 > 4단계`를 이어 붙인다. 안전주의 섹션은 `경고`와 `주의`
아래에 같은 소제목(`제품을 설치할 때`)이 반복되므로 이렇게 해야 구분된다.

### 고장신고 표: 증상 1개 = 청크 1개

`parse_troubleshooting()`은 여전히 `find_tables()`로 `[증상, 원인 및 해결책]` 표를 읽지만,
같은 증상에 딸린 원인·해결책 행을 **전부 한 청크로 합친다**. 증상이 페이지를 넘어가면 다음
페이지 표에 증상명이 다시 찍히는데, 이 경우도 직전 증상과 같으면 이어 붙인다.

- 청크 수 471 → 211 (모델당 20~27개)
- 와이파이 증상 1청크 = 920자 (원인 6개 전부)
- 표 셀 안의 레이아웃용 줄바꿈은 공백으로 펴고 `•` 앞에서만 줄을 나눔

### 나머지

| 항목 | 변경 |
|---|---|
| 페이지 번호/러닝헤더 | `strip_page_furniture()` — 페이지 앞머리의 숫자 줄과 챕터명 줄 제거 (locate_sections는 원문을 봐야 하므로 본문 조립 시점에만 적용) |
| `chunk_id` | `hashlib.md5(body)[:8]` — 재시작해도 동일 |
| `split_oversized()` | 줄 경계에서 자르고 100자 오버랩 |
| `TOP_LEVEL_SECTIONS` | `"사용하기"` 추가 (SQ 벽걸이형). `HOWTO_SECTIONS`로 숨은 헤더 감지 대상 지정 |
| `category_for_table()` | 표 위에 제목 없으면 **직전 카테고리 유지** |
| 임베딩 텍스트 | breadcrumb에서 `[doc_id]` 제거 — 한 문서의 모든 청크가 공유하는 값은 벡터에 정보가 없고 모델 필터는 메타데이터로 걸림 |
| 색인 제외 | `SKIP_GROUPS` = 오픈소스 정보 / 폐가전제품 처리 절차 / 생활 속 전기안전 캠페인 |
| 고장 진단하기 | 이전엔 표만 읽어서 `LG ThinQ로 고장 진단하기` 같은 텍스트가 **통째로 누락**됐음 → `parse_by_toc(skip_groups={"문제 해결하기"})`로 텍스트 부분도 색인 (`tag="diagnosis"`) |

### 에러코드(CH04, CH05 …)는 별도 JSON을 1항목 = 1청크로 색인

COMMON_QUESTIONS 검색 히트율(45%, 10/22)을 뜯어보니 LG 에어컨 범위 8개 중 매뉴얼에 있는 4개는
전부 맞았고, 틀린 건 **에러코드 질문 2개**(`CH04`, `실내기-실외기 통신 에러`)였다. 10개 PDF를
`CH\d+`/`에러코드`로 전부 훑어도 0건 — 매뉴얼의 "문제 해결하기"는 증상 기반 표만 있고 CH 코드는
`data/lg_aircon_errors.json`(LG 고객지원 안내, 11항목)에 따로 있다.

- `load_error_code_chunks()` — JSON `sections[].{title, content}`를 파싱 없이 그대로 청크로.
  `section="에러코드"`, `subsection=title`, `tag="error_code"`
- 특정 모델 매뉴얼이 아니라 LG 에어컨 공통이므로 `doc_id="LG-AC-COMMON"`으로 넣고,
  `_as_filter()`가 어떤 모델을 골라도 `{"doc_id": {"$in": [모델, "LG-AC-COMMON"]}}`로 항상 포함.
  `known_doc_ids`(사용자가 고를 수 있는 모델 목록)에서는 제외
- 전체 재임베딩 없이 `vectorstore.add_documents(..., ids=...)`로 11개만 추가 (셀 16). 기존 공통 청크를
  지우고 다시 넣기 때문에 여러 번 실행해도 안전
- `Chroma.from_documents(..., ids=[c["id"] ...])` — 청크 id를 Chroma id로도 써서 나중에 개별 삭제/교체 가능

확인 결과 (`AC_FQ18GC1EHN` + 공통, L2 거리):

| 질문 | top-1 | 거리 |
|---|---|---|
| CH05 에러가 떴어요 | ✅ `CH05 / E0 / CH53 (통신 에러)` | 0.655 |
| 에어컨에서 CH04 에러가 떴어 | ✅ `CH04 / FL (배수 불량, 만수 감지)` | 0.569 |
| 실내기랑 실외기 통신 에러 나요 | ✅ `CH93 (실내기·실외기 통신 이상)`, #2 CH05 | 0.635 |
| 취침 / 와이파이 (기존 질문) | 변화 없음 | — |

### 검색 쪽 (앞선 작업)

- `search(query, doc_id=None, top_k=3)` — 질문에서 모델명을 추출하지 않고 **`doc_id`를 명시적으로** 받음.
  웹에서는 사용자가 가전을 등록해두므로 모델은 질문과 별개로 들어온다.
- `doc_id`는 `str | list[str] | None` (여러 대 등록 → `$in` 필터). 없는 모델명은 `ValueError`
  (Chroma는 없는 값으로 필터하면 조용히 빈 결과를 줘서 오타를 못 알아챔)
- `make_answer_fn(doc_id)` — `run_and_save()`는 `my_answer(query)` 인자 하나만 넘기므로 클로저로 감쌈

### 자체 테스트셋 (`testset.json`, 63케이스)

COMMON_QUESTIONS는 제품군이 섞여 있어 LG 에어컨 검색 품질을 재기엔 부족해서, 웹 시나리오
(등록된 모델 + 구어체 질문)를 흉내낸 테스트셋을 따로 만들었다. 질문은 소제목을 베끼지 않고
사용자가 칠 법한 말로 썼다 (`"버튼 누를 때 삐 소리 안 나게 하는 방법"` → `음량 설정하기`).
모델 3개(FQ18GC1EHN, FQ25GN9BKN 상위, SQ09GK1WEN 벽걸이) + 에러코드 공통.

| 카테고리 | n | top-1 | hit@3 | MRR |
|---|---|---|---|---|
| care (관리) | 11 | 82% | 100% | 0.89 |
| error_code | 7 | 100% | 100% | 1.00 |
| howto (사용법) | 18 | 83% | 94% | 0.87 |
| info (보증/구매) | 3 | 67% | 67% | 0.67 |
| safety | 3 | 67% | 67% | 0.67 |
| symptom (증상) | 17 | 82% | 88% | 0.85 |
| **전체** | **59** | **83%** | **92%** | **0.86** |

1등이 아닌 10개의 성격:
- 어휘 간극 — `말로 조작` ↔ `음성인식`, `이사` ↔ `이전 설치`, `혼자 켜졌어요` ↔ `갑자기 작동해요`: top-3 밖. bge-m3 한계. 동의어 확장이나 하이브리드(BM25) 검색 후보
- 증상 행 vs 사용법 경쟁 — `빨리 시원하게` 질문에 `시원하지 않아요` 증상이 1등, `아이스 쿨파워`는 3등. `실외기 조용하게` 도 소음 증상 행이 위. 증상 행이 짧고 구어체라 구어체 질문에 유리함
- `타는 냄새` → `냄새 제거하기`(1등)가 안전 경고(`제품 이상 및 고장이 발생했을 때`)를 이김. 안전 청크가 162자로 짧고 "타는"이란 단어가 없음
- 비슷한 증상 4개가 경쟁 — `종합 청정도` 증상 4개 중 정답이 4등

**"기능 없음" 거리 임계값은 깔끔하지 않다**: 정답 1등일 때 top-1 거리 0.44~0.94, 없는 기능 물었을 때 0.86~0.98 →
겹침. 0.85면 없음 4/4 잡고 정답 3/49 오판. 임계값은 보조로만 쓰고 최종 판정은 LLM이 근거 문서 보고 하게 두는 게 맞다.
대안: 부록 `모델별 기능 확인하기` 표(FQ**GC2*** … O/X)를 메타데이터로 뽑아 기능 유무를 룰로 판정.

### 고도화 검색: 질문 확장 + (코드 한정) BM25 + 리랭커 — 노트북 5-2절

baseline 1등 실패 10건을 ① 어휘 간극 ② 정답 2~3등 ③ 정확 단어 매칭 필요로 나누고, 각각에 대응하는 기법을
**같은 테스트셋으로 전부 실측**해 골랐다 (3모델 297청크, CPU):

| 구성 | top-1 | hit@3 | MRR | 초/질문 |
|---|---|---|---|---|
| baseline (bge-m3 벡터만) | 83% | 92% | 0.86 | 0.05 |
| +리랭커만 (bge-reranker-v2-m3) | 86~90% | 92~93% | 0.89~0.92 | 3.6~7.2 |
| +BM25 항상 (RRF 동일 가중) | **66%** ↓ | 80% | 0.72 | 0.05 |
| +질문확장만 (RRF) | 83% | 95% | 0.88 | 0.10 |
| 전부 (n=12, 512토큰) | 86% | 97% | 0.91 | 7.2 |
| **질문확장 + 리랭커 (n=8, 384토큰)** | **88%** | **100%** | **0.94** | 3.6 |
| + 코드 있을 때만 BM25 | 88% | 100% | 0.94 | 3.6 |

배운 것:
- **리랭커가 가장 큰 단일 효과.** 후보 12→8, 길이 512→384로 줄이니 더 빠르고 더 정확했다 — 후보가 많으면 리랭커가 잡음에 흔들림
- **문서 쪽 질문 확장**(청크마다 gpt-4o-mini로 "물어볼 법한 질문" 4개 생성 → 별도 컬렉션 임베딩, `parent_id`로 청크 복귀)이
  어휘 간극을 실제로 메움: `말로 조작`→`음성인식`, `이사`→`유상 서비스` 가 top-1로. 오프라인 1회라 서비스 응답 시간 영향 없음.
  캐시 `chunk_questions.json` (커밋 대상). 처음 297청크는 옛 프롬프트로 생성돼 "에러코드가 뭐죠?" 류 잡음 질문이 일부 섞여 있음
  — 이후 생성분은 "내용에 없는 것 지어내지 마라" 규칙이 들어간 프롬프트. 성능엔 영향 없었지만 재생성하면 더 깔끔
- **BM25는 항상 섞으면 해롭다** (-17pt). 구어체 질문의 흔한 단어("에어컨", "어떻게")가 무관 청크를 끌어올림. 질문에 `CH05`/`E6` 같은
  코드가 있을 때만 켬(`CODE_RE`) — 이 경우엔 정확 매칭이 임베딩보다 안정적
- **"기능 없음" 판정은 점수로 안 된다**: 임베딩 거리도, 리랭커 확률도 정답/기능없음 분포가 겹침 (리랭커 정답 1등 확률이 0.005까지 내려감).
  룰(부록 `모델별 기능 확인하기` 표) 또는 LLM 판단으로 넘겨야 함
- 남은 1등 실패 7건은 전부 2등 이하가 아닌 **2~3등**이고 대부분 "둘 다 그럴듯": `먼지통 비우기` vs `먼지통 알림 초기화`,
  `타는 냄새` → 냄새 제거(관리) vs 안전 경고, `가스 냄새` → 안전 경고가 2등

비용/속도: 리랭커 CPU 3.6초/질문은 웹 서비스엔 느림. GPU면 0.1~0.2초. 대안: 더 작은 리랭커, 또는 후보 5개로.
