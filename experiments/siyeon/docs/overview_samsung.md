# 삼성 가전 설명서 — 청킹·검색 전략, 쉽게 설명하기

> RAG나 검색 기술을 잘 모르는 사람을 위한 문서입니다.
> **LG편(`docs/overview_lg.md`)을 먼저 읽으면 좋습니다** — 기본 개념(왜 잘라야 하나, 벡터 검색이 뭔가, 검색 4단계)은 거기 있고,
> 이 문서는 **삼성에서 무엇이 달랐고 어떻게 맞췄는지**만 다룹니다. 실험 수치·실패 기록은 `docs/experiment_notes.md`, 코드 위치는 `siyeon/docs/code_map.md`.

---

## 0. 결론 먼저

삼성 설명서 30개도 **LG와 같은 전략("설명서 목차대로 자르기")이 그대로 통했습니다.** 파서를 따로 만든 이유는 전략이 달라서가 아니라,
**"목차를 어디서 얻고 얼마나 믿을 수 있나"** 와 **"고장 해결 부분이 표인가 글인가"** 두 가지가 달라서입니다.

- 삼성 30개 전부 청킹 완료 → **2,213조각** (LG 30개 2,833조각과 합쳐 인덱스 총 5,046조각)
- **검색 쪽은 코드 변경 없음** — 등록 모델로 필터 → 에러코드는 DB 조회 → 벡터 검색 + 리랭커, LG와 완전히 같은 흐름
- 팀 평가 900문항 중 삼성 450문항이 **448/450 자기 매뉴얼로 답하는 상태** (exp05)

## 1. 먼저 30개를 전부 열어봤습니다

파서를 짜기 전에 30개 PDF의 구조를 스캔했습니다. "삼성은 이렇다"고 한 번에 말할 수 없었기 때문입니다.

| 확인 항목 | 결과 |
|---|---|
| 제작 도구 | Adobe InDesign (LG는 FrameMaker) |
| 목차(북마크) 내장 | **27/30** — 나머지 3개는 아예 없음 |
| 목차 소제목이 본문 줄과 글자 그대로 일치 | 거의 100% (LG와 같음) → **목차 경계로 자르는 전략이 통한다는 근거** |
| 챕터 이름 체계 | **제품군·세대마다 다름.** 에어컨만 3계열: `주의하기/살펴보기/명칭알기/사용하기/문제해결…` / `스마트 에어컨 살펴보기/간편하게 조절하기/똑똑하게 사용하기…` / `준비편/운전편/청소편/기타편` |
| 고장 해결 부분 | **제품군마다 형식이 다름** (아래 3절) |
| 굵은 글씨 사용 | 거의 안 씀 — 소제목을 **글자 크기**로만 구분 |
| 띄어쓰기 | 1개 문서(`RF_SRS705IC`)가 `냉장실의냉기가잘나오게하려면`처럼 공백 없음 |

## 2. 챕터를 어떻게 찾았나 — "목차를 믿되, 확인한다"

LG는 챕터 이름이 11개로 통일돼 있고 챕터 시작 페이지에서 이름이 **두 줄 연속 반복**되는 규칙이 있어서 그걸로 찾았습니다.
삼성은 챕터 이름을 미리 정해둘 수 없어서(위 3계열) **목차 1단계의 페이지 번호**를 씁니다.

그런데 목차를 그대로 믿으면 안 되는 문서가 있었습니다:

```
RF_RH82M9152SL (삼성 냉장고)
  목차: '냉장고 관리하기' → 0페이지      ← 페이지 번호가 아예 없음
        '고장신고 전 확인하기' → 63페이지  ← 실제로 63페이지는 "냉장고 치수" 표
        '이온살균청정기의 기능 (해당 모델만 참조하세요.)'  ← 본문 제목엔 괄호 부분이 없음
```

그래서 **목차에 적힌 제목을 본문에서 실제로 찾아 페이지를 확정**합니다 (`chapters_from_toc`). 목차가 가리킨 페이지와 그 다음 페이지를 먼저 보고,
없으면 문서 전체를 훑습니다. `(해당 모델만 참조하세요.)` 같은 괄호 접미사는 뗀 형태도 함께 찾습니다.

챕터의 **역할**(사용법인지 고장 해결인지 안전 주의인지)은 이름 정확 일치 대신 **키워드**로 판단합니다:

| 챕터 이름에 이 단어가 있으면 | 이렇게 처리 |
|---|---|
| `고장`, `문제`, `점검`, `해결` | 고장 해결 파서 (3절) |
| `주의`, `안전` | 안전 주의사항 (`safety` 태그) |
| 그 외 | 목차 소제목 경계로 자르기 (LG와 같은 함수 재사용) |

## 3. 고장 해결 부분 — 제품군마다 형식이 세 가지

여기가 삼성에서 가장 손이 많이 간 부분입니다. 사용자가 "탈수가 안 돼요" 같은 질문을 가장 많이 하므로, 이 부분을 **증상 1개 = 조각 1개**로 만드는 게 중요합니다.

### (a) 세탁기·건조기·스타일러·슈드레서 — 표 2종

```
증상          | 확인/조치
전원이 들어오지 않아요. | • 전원 플러그가 꽂혀 있는지 확인하세요. …

코드 | 진단                      | 해결방법
[■] | 급수가 되지 않아요.          | • 수도꼭지가 열려 있는지 확인하세요. …
```

LG와 같은 방식으로 표를 읽어 증상 단위로 묶습니다. 단 **`코드` 열은 그림(이미지)이라 글자가 안 나옵니다** — 그래서 코드 대신 `진단` 문장을 증상으로 씁니다.
코드로 찾는 질문(`UE 떴어요`)은 어차피 SQLite 에러코드 표가 담당하므로 손실이 없습니다.

### (b) 냉장고 일부 — 표에 카테고리 열이 하나 더

```
카테고리   | 증상                      | 원인 및 해결책
소음      | 물 흐르는 소리가 나요!        | …
온도, 성능 | 냉장실 식품이 얼어요.         | …
```
카테고리를 조각 라벨에 넣어 `소음 > 물 흐르는 소리가 나요!` 처럼 만듭니다.

### (c) 에어컨 대부분 + 냉장고 대부분 — **표가 아니라 그냥 글**

이게 까다로웠습니다. 표가 없으니 "어디까지가 한 증상인가"를 글에서 알아내야 합니다. 두 가지 신호를 씁니다:

**신호 1 — 글자 크기** (삼성 에어컨)
```
13pt  전원                          ← 카테고리
11pt  전원이 켜지지 않아요.            ← 증상  (본문보다 1.3pt 큼)
9.7pt • 콘센트가 잘 연결되었는지 …      ← 본문
9.7pt • 반드시 전용 콘센트를 사용해 …
11pt  전원이 꺼지지 않아요.            ← 다음 증상
```
본문보다 큰 줄을 증상으로 봅니다.

**신호 2 — 말투 + 다음 줄** (삼성 냉장고 — 증상과 본문의 글자 크기가 같음)
```
10pt  냉장고 안에서 '뚝'하는 소리가 나요! (뚝, 딱, 뚜둑 등)   ← '~나요!' 로 끝나고
10pt  ꞏ 냉장고 안의 온도가 변할 때 부품이 …                 ← 다음 줄이 점(불릿)으로 시작 → 증상으로 판정
```

**주의해서 뺀 것**: `~하세요.`로 끝나는 줄은 증상이 아니라 **안내문**입니다 (`서비스 센터에 연락하세요.`).
처음엔 `~요.`로 끝나는 줄을 전부 증상으로 봤다가 안내문이 증상으로 잡혀서, 명령형 어미는 제외했습니다.
또 글자 크기로 증상이 구분되는 페이지에서는 말투 규칙을 껐습니다 (두 규칙이 충돌하면 크기가 더 정확).

## 4. 목차가 없는 3개 — 글자 크기로 소제목 찾기

`RF_RP20C3111S9`, `RF_SRS705IC`, `WM_WF21T6500KW`는 목차 북마크가 아예 없습니다. LG 구형 3개와 같은 폴백 파서를 쓰는데,
**차이는 굵은 글씨입니다** — LG 구형은 소제목을 굵게 썼지만 삼성은 굵게 쓰지 않아서 "본문보다 1pt 이상 큰 짧은 줄"을 소제목으로 봅니다.
`주 의`, `참 고` 같은 알림 상자 제목은 제외합니다.

띄어쓰기가 없는 `RF_SRS705IC`는 kiwi 형태소 분석기로 띄어쓰기를 복원해서 임베딩합니다
(`냉장실의냉기가잘나오게하려면` → `냉장실의 냉기가 잘 나오게 하려면`).

## 5. 결과

| 삼성 제품군 | PDF | 조각 수 | 증상 조각 | 증상을 잡은 방식 |
|---|---|---|---|---|
| 에어컨 | 10 | 564 | 61 | AF17B·AR11B 계열은 글자 크기로. 나머지 7개는 문제해결이 `부록` 아래 소제목이라 사용법 조각으로 들어감 |
| 냉장고·김치냉장고 | 10 | 758 | 215 | 표(2개) + 글자 크기·말투(8개) |
| 세탁기·건조기·스타일러·슈드레서 | 10 | 866 | 213 | 전부 표 (`증상｜확인/조치` + `코드｜진단｜해결방법`) |
| 에러코드 (JSON 3개) | — | 25 | — | `SAMSUNG-AC/RF/WM-COMMON` 공통 문서 |
| **합계** | **30** | **2,213** | **489** | |

조각 길이 중간값은 159~1,187자 (목차가 촘촘한 문서는 짧고, 폴백 파서 문서는 깁니다).

**잡았던 버그 하나** — 냉장고 문제해결 **첫 페이지의 증상 7개가 통째로 누락**되고 있었습니다. 그 페이지에서 절 제목
`안심하세요! 고장이 아닙니다`(11pt)가 본문(10pt)보다 커서 "이 페이지는 글자 크기로 증상을 구분한다"고 오판하고 말투 규칙을 껐던 탓입니다.
절 제목(목차 제목)을 판정에서 제외하니 `RF_RS84B5041WW` 증상이 15 → 30개로 복구되고, `RF_RF85B90P1AP`는 PDF의 실제 증상 54개 중 **누락 0건**이 됐습니다.
자체 테스트셋에서 삼성 증상 질문 hit@3가 83% → **100%** 로 올랐습니다.

## 6. 검색 — 코드 변경 없음

`retrieve()` 흐름(등록 모델 필터 → 에러코드 DB 조회 → 기능 유무 판정 → 벡터 검색 + 리랭커)은 **LG와 완전히 같습니다.**
삼성 때문에 바꾼 건 두 줄뿐입니다:

1. **공통 에러코드 문서를 브랜드별로** — 삼성 세탁기 사용자는 `SAMSUNG-WM-COMMON`을, LG 세탁기 사용자는 `LG-WM-COMMON`을 봅니다.
   `UE`가 삼성 세탁기에선 "불균형 감지", LG 세탁기에선 "불균형, 탈수 안됨"으로 내용이 다르므로 섞이면 안 됩니다.
2. **매뉴얼 없는 모델의 폴백을 같은 브랜드로 제한** — 삼성 모델 질문에 LG 매뉴얼이 후보로 오지 않게.

**기능 유무 판정(②단계)은 삼성에선 자연히 건너뜁니다.** LG 설명서 부록에 있는 `모델명 | 클린봇 | UVnano | O/X` 같은 표가
삼성엔 없어서, 판정 근거가 없으면 그냥 검색으로 넘어가도록 이미 설계돼 있습니다.

## 7. 한계와 다음 단계

- **삼성 에어컨 7개 모델**(`AF18RX`, `AF19TX`, `AR06A`, `AR06R`, `AR09T`, `AM145J`, `AR-EH05`)은 문제해결이 `부록` 챕터 아래 소제목으로 들어 있어
  조각은 만들어지지만 `증상` 태그가 아니라 `사용법` 태그입니다. 검색 자체엔 영향이 없지만(같은 내용이 색인됨), 증상 통계에는 안 잡힙니다.
- **`코드｜진단｜해결방법` 표의 코드가 이미지** — 매뉴얼 자체에서 코드를 못 읽으므로 코드 질문은 SQLite(삼성 3제품군 25항목)에만 의존합니다.
  매뉴얼에만 있고 JSON에 없는 코드가 있다면 답할 수 없습니다. 확인 필요.
- **부록 기능 표 없음** — "이 모델에 그 기능이 있나"를 룰로 판정할 수 없어, 없는 기능 질문엔 LLM이 "문서에 없습니다"로 답하게 됩니다.
  팀 평가에서 삼성 문항 78/450이 그런 답변이었는데, 정말 없는 기능인지 관련도 컷이 과한지 확인이 남았습니다.
- **삼성 김치냉장고·슈드레서**는 제품군 특성 질문(`김치 발효 코스`)에서 어휘 차이가 있습니다 (`발효` vs 설명서의 `숙성`).
